# ADR 0022: Application Update Delivery

- Status: Accepted (amended by D364 / D603 / D628 / ADR 0197, D450 / ADR 0289, D659, D668; issue #1098)
- Date: 2026-07-26
- Deciders: Minih-Agent-Desktop core
- Related: D120, D126, D364, D603, D628, D010, D450, ADR 0021, ADR 0197, ADR 0289

## Context

Minih-Agent-Desktop needs a release-update path that preserves the renderer sandbox,
does not expose feed configuration to untrusted UI code, and reflects each
platform's actual installer capabilities. A single automatic-install policy is
not appropriate: unsigned macOS packages cannot provide a qualified in-app
upgrade lane, while Windows NSIS and Linux AppImage support electron-updater's
download-and-install flow.

## Decision

1. Electron Main exclusively owns `electron-updater`, the fixed GitHub
   Releases feed, update polling, and install lifecycle. Renderer IPC exposes
   only allowlisted check, state, release-link, and install operations; callers
   cannot supply a feed URL.
2. Development builds keep updates disabled. Packaged macOS, Windows NSIS, and
   Linux AppImage use in-app download and quit-and-install delivery. Non-AppImage
   Linux (deb/rpm) and Windows ZIP builds (`piDistribution = "zip"`) use
   notify-and-link delivery so an NSIS installer cannot replace a no-install
   run. Legacy portable executables remain manual when
   `PORTABLE_EXECUTABLE_FILE` is present. (Packaged macOS was notify-and-link
   until D450 / ADR 0289 qualified the signed in-app channel.)
3. The updater always sets `allowPrerelease = false`. electron-updater would
   otherwise pin prerelease installs (for example `0.2.0-rc.6`) to the same
   custom channel (`rc`) and never offer a newer stable GitHub latest release.
   Prerelease-channel policy remains an operational follow-up if a dedicated
   RC feed is needed later.
4. Automatic checks run after startup and periodically. Automatic failures
   remain ambient; explicit checks expose status and errors through the menu
   and Settings -> Info. A downloaded update remains actionable until install
   or normal shutdown.
5. Feed manifests and artifact hashes are generated by electron-builder. The
   client ships no GitHub credential and fails closed when the feed or package
   cannot be validated.
6. D126 later lifts D010's macOS-only publication scope and publishes all
   platform artifacts and update manifests produced by the release matrix.
   D450 / ADR 0289 qualifies the signed macOS in-app channel on that same feed.
7. Dual-locale product "what's new" text (D164) is maintained in
   `packages/shared` as EN + zh-CN catalogs. Main formats notes for the
   discovered version using the product UI locale and attaches them as optional
   `UpdateState.releaseNotes` on the existing updates path. GitHub auto-generated
   release bodies remain web-only; the renderer never supplies a notes URL.

## Consequences

- Update state is process-owned and consistent across the application menu,
  Settings, and the ambient banner.
- The sandboxed renderer cannot redirect update traffic or install arbitrary
  packages.
- Windows NSIS, Linux AppImage, and packaged macOS can update in-app from
  published tag feeds; Linux deb and Windows ZIP users install from the
  release page after extracting the archive.
- Prerelease installs graduate to newer stable releases through the same
  latest feed; a dedicated RC channel is not active.
- In-app bilingual release highlights ship with the build and follow the
  product locale without a second network surface.
- Rollback, staged rollout, and optional prerelease-channel policy remain
  operational follow-ups rather than renderer capabilities.

## Alternatives

- Renderer-owned updater: rejected because it violates the process and
  sandbox boundary.
- Caller-provided feed URLs: rejected because it creates an arbitrary package
  installation path.
- Force one delivery mode on every platform: rejected because installer and
  signing guarantees differ by target.

## Amendment (D450 / ADR 0289)

Official GitHub tag macOS artifacts are Developer ID-signed, notarized, and
stapled. Packaged macOS therefore uses the same in-app `electron-updater` lane
as Windows NSIS and Linux AppImage. Local unsigned packaging without a
certificate remains available (D078).

## Amendment (D603)

The Windows no-install lane now publishes a normal ZIP archive instead of
electron-builder's self-extracting `portable` executable. The release helper
builds NSIS and ZIP separately and stamps the ZIP app metadata with
`piDistribution = "zip"`; the updater uses that marker to keep the ZIP manual
even though ordinary ZIP launches do not set `PORTABLE_EXECUTABLE_FILE`. Users
extract the archive and run `Minih-Agent-Desktop.exe`; the NSIS lane and existing data
directory remain unchanged.

## Amendment (issue #1098)

For Windows NSIS installs, `MINIH_AGENT_UPDATE_CACHE_DIR` may set an absolute,
writable base for electron-updater's download cache. Main reads the cache's
subdirectory name from the packaged `app-update.yml`, adopts the installer and
block-map differential baselines plus any staged update from `%LOCALAPPDATA%`
on startup, then removes the legacy cache directory only when empty. Unknown
files and already-populated destinations are preserved rather than overwritten
or recursively deleted. Once the feed confirms the running version is current,
Main deletes only the obsolete `pending/` staging directory and keeps the
baselines for the next differential update. The default
cache location remains unchanged unless the variable is set. Main does not write
to the installation directory: the NSIS script still writes its `installer.exe`
baseline to `%LOCALAPPDATA%`, which Main adopts on the next launch.


## Amendment (D628)

Settings → Info exposes a persisted per-install `updatePreference` with
`automatic` and `manual` values. Automatic preserves the existing in-app
installer lane. Manual continues stable-release checks but disables automatic
download and install-on-quit, and raises one reminder per discovered version.
The last reminded version is stored in the existing Host-owned app settings
JSON and is intentionally omitted from portable configuration sync.

An update-banner dismissal is also persisted for its available version. In-app
dismissal cancels an active download and disables install-on-quit for that
version. Scheduled and explicit checks continue; rediscovering the dismissed
version does not restart its download, while discovering a newer version clears
the dismissal and restores automatic delivery.

Installed Windows NSIS, packaged macOS, and Linux AppImage default to Automatic.
Windows ZIP/portable packages default to Manual; opting into Automatic is
available on supported Windows packages only after the UI warns that NSIS may
replace the extracted no-install copy. Unsupported installer formats remain
Manual. This additive setting requires no database schema or host protocol
version change.

## Amendment (update mirrors and download resilience, D659)

GitHub Releases stays the canonical feed. A release may now compile in a fixed,
ordered list of HTTPS mirrors (`MAIN_VITE_MINIH_AGENT_UPDATE_MIRRORS`, at most
three) so installs on networks that throttle `github.com` can still reach the
same release:

1. Every mirror hosts the same `latest*.yml` files, installers, and blockmaps as
   the GitHub Release for that version. `scripts/publish-update-mirror.mjs`
   dual-writes them after the Release is published, artifacts first and feeds
   last with `Cache-Control: no-cache`. A mirror changes the host, never the
   release.
2. Main owns the list. It is compiled into the bundle, validated at startup
   (absolute `https`, no credentials, no query or fragment, not `github.com`),
   and applied only through `setFeedURL`. The renderer and runtime settings
   cannot supply or extend a feed; unusable entries are logged and ignored, and
   a build without mirrors keeps exactly the packaged GitHub feed.
3. Sources are tried in order — the packaged GitHub feed first, then the
   compiled-in mirrors (D668 moved the packaged feed behind both accelerator
   layers; see the D668 amendment below). The host that answered stays
   preferred for the session, and a failing check moves the preference to the
   next source. The retry itself waits for the failed request to settle
   (bounded), so only one check is ever in flight and a request that hangs past
   the check window and then succeeds cannot download from a host the desktop
   has already left.
4. A download that stops reporting progress is cancelled after 45 s and retried
   once against the next source; a second stall for the same version reports
   `errorCode: "download-stalled"`. An installer failure while bytes were in
   flight also moves the preference on rather than retrying the broken host.
5. The updater's own Chromium partition is registered with the network-proxy
   module (ADR 0177), so update traffic follows Settings → Network on the first
   check and after a proxy change without waiting for the next app start.
6. `UpdateState` gains `errorCode` (`check-timeout` or `download-stalled`) and
   `feedHost`. Both are additive optional fields: the renderer localizes a
   failure it understands and keeps the raw text otherwise, and support can see
   which host served the update.

Mirror trust: the feed a client reads binds the artifact hashes it verifies, so
a mirror that serves both the manifest and the bytes is trusted for that release
in the same way the on-disk `app-update.yml` provider is trusted. Windows
packages are unsigned today, which makes a configured mirror the trust anchor on
that lane; Windows code signing (`forceCodeSigning` writing `publisherName`) is
the prerequisite for treating a mirror as untrusted, and stays a release
follow-up.

## Amendment (server-published accelerators, D668)

The router publishes a public, credential-free, read-only accelerator list at
`GET <router origin>/api/desktop-update`, and a minih build now tries it before
anything else:

1. `data.sources[].prefix` entries are prefix-style GitHub accelerators
   (`https://gh-proxy.org/`). Main expands each one into a generic feed base
   (`<prefix>https://github.com/<owner>/<repo>/releases/latest/download`) and
   validates it exactly like a compiled-in mirror: absolute `https`, no
   credentials, no query or fragment, not `github.com`, deduplicated, at most
   three entries. An unusable entry is dropped on its own; a payload that is not
   the expected envelope yields no accelerator at all.
2. Source order for a minih build is now: router accelerators (in the order the
   endpoint published), compiled-in mirrors
   (`MAIN_VITE_MINIH_AGENT_UPDATE_MIRRORS`), then the official GitHub feed. The
   official feed is always last, so a failing accelerator still resolves the
   update.
3. The list is refreshed before a check and memoized for the TTL the endpoint
   published (`ttl_seconds`, clamped to 1 minute … 24 hours; 1 hour when
   absent). A failed fetch is logged as a warning, pauses the next attempt for
   at least 5 minutes, and never fails, delays, or blocks the check — the
   sources already in use keep working. A list that arrives while an installer
   is downloading is applied by the next check instead of repointing the
   updater mid-transfer.
4. Withdrawing the list takes effect the same way: when the endpoint returns no
   accelerator after one served the updater, Main re-applies the official
   GitHub feed explicitly and as the only source. The packaged feed carries no
   URL, so it cannot revoke a feed already applied through `setFeedURL`; without
   this step a withdrawn accelerator would stay in use until the app restarted.
5. The list is honored only when the brand's packaged feed is GitHub
   (`currentBrandProfile().updateFeed.provider === "github"`). A hungraim build
   keeps its generic `updates.hungraim.com` feed, ignores the router list, and
   makes no request to it. `MINIH_AGENT_UPDATE_SOURCES_URL` overrides the
   endpoint URL so a local or self-hosted gateway can be verified without
   repackaging.

Cost, stated plainly: an accelerated check reads the channel files
(`latest*.yml`) from a third-party community site, so the version and hash
anchor move to that site for that check. electron-updater still verifies the
installer against the `sha512` in the yml it read, and Windows and macOS still
verify their own signatures, but an accelerator that serves both the manifest
and the bytes is trusted for that release in the same way a configured mirror
is (see the mirror-trust note above), and Windows packages remain unsigned
today. The official GitHub feed stays the last source and the canonical
artifact origin, and Main still owns the list: the renderer and runtime
settings cannot supply, extend, or redirect it.
