## 背景

插件面对于「读取、转换、展示」类插件是完整的：文件、会话、Provider、模型、主题、
面板、总线。对另一类插件则是空的——那类插件的职责是**替用户持有**某样东西：
一个邮件服务器的 API 令牌、一个数据库套接字、一个别人往里投递的信箱地址、一个
时钟、一个插件自己发起的任务、用户收件箱里的一行。

今天这些全部建在**插件进程内部**，因为 `manifest.main` 带着完整的 Node 内置模块
运行（ADR 0008 D009）。插件可以自己开 TCP 套接字、自己监听一个端口、把令牌存在
自己的设置文件里。这不是宿主能审查、审计或收回的边界：用户看不到持有什么，安装页
不会出现任何权限，禁用插件也不一定关掉它开出去的东西。

由此得出的设计规则，与宿主已经自持的几个面（`net.websocket`、
`keyboard.globalShortcut`、ADR 0115 的剪贴板历史）一致：**资源由宿主持有，插件
通过权限和句柄使用。** 密钥、监听套接字、公开路径、定时器、任务、信箱条目，都是
宿主状态。代理 API 不直接交出保存的凭据、套接字或时钟；这不是操作系统隔离（§3）。

六组能力覆盖了第一方插件作者提出的需求。没有一项能用现有权限表达，其中两项若作为
无名的插件行为则相当危险：插件自开的端口不会出现在任何权限列表里，插件自持的密钥
是用户无法在设置里轮换的令牌。

## 决策

### 1. 八个权限，六组能力

| 组 | 权限 | manifest 字段 | 宿主持有的资源 |
|---|---|---|---|
| 凭据 | `credentials.use` | `contributes.credentials` | 密钥值 |
| 原始 TCP | `net.tcp` | `net.tcp` | 套接字 |
| 入站 webhook | `inbound.webhook` | `contributes.webhooks` | 监听、路径、令牌 |
| 定时器 | `scheduler` | `contributes.schedules` | 时钟 |
| 宿主写入列表 | `mail.draft`、`notify.center` | — | 列表及其行 |
| 任务 | `tasks.read`、`tasks.manage` | `tasks` | 任务及其会话 |

每个名字都加进 `PLUGIN_PERMISSIONS`，每个名字都在 `PLUGIN_PERMISSION_RISK`
里有风险等级。等级表是一个
`satisfies Record<PluginPermission, PluginPermissionRisk>` 约束，因此新增权限
却忘了等级是**编译错误**，而不是一个看上去无害的能力混进安装页。**未识别**的
权限名读作 `high`（`pluginPermissionRisk`）：宿主无法归类的能力，绝不能显得比
能归类的更安全。

风险分级：

- **high** —— `credentials.use`、`net.tcp`、`inbound.webhook`、`tasks.manage`。
  宿主代插件持有密钥、套接字、公开路径或任务，所以授予权限本身就是全部边界。
- **medium** —— `scheduler`、`mail.draft`、`notify.center`、`tasks.read`。
  宿主持有的是一条用户看得见、也能停掉的有界队列；写草稿从不发送，定时器不花
  额度，读取路径没有写入能力。

### 2. 权限是开关，manifest 是范围

与 `net.domains`、`manifest.fs` 同一条规则：权限名回答「能不能做」，manifest
字段回答「能做到多远」，两者在安装页并排展示，而且**字段缺失就什么都不授予**。
没人能用的字段会让 manifest 校验失败，而不是被悄悄忽略。

### 3. 宿主强制执行的边界

以下是护栏。每一条都由宿主执行、不由插件自律，并且都在安装审查里写明。

**凭据（`credentials.use`）。**

- 槽位由用户在设置里填写，插件不能通过宿主 API 写入。**没有凭据读取 API**；
  宿主生成的响应、错误和审计记录不披露保存的值。
- 值存在既有的密钥库，不进 SQLite（规格 03-runtime/04 §10）；静态存储方式不变。
- 只在插件用 `credentialRef` 点名的宿主持有出网路径上注入，且目标必须同时落在
  槽位 `scope` 与插件自己的声明内：HTTP 与 WebSocket 看 `manifest.net.domains`，
  IMAP 登录看 `manifest.net.tcp` 端点。没有 `scope` 的槽位无处注入。
- 这是可审计的 API 边界，不是操作系统沙箱，不能防范具有用户文件权限和原生 Node
  能力的恶意插件；请只安装信任的插件。远端服务可能在响应体、WebSocket 帧或
  IMAP 登录后的 TCP 流中回显凭据，宿主不过滤这些应用数据。
- 设置面板渲染不出来的槽位（没有 kind、没有字段、字段 key 重复）会让 manifest
  校验失败：无法使用的权限是作者的疏忽。

**原始 TCP（`net.tcp`）。**

- 端点是字面的 `{ host, port, tls }`。没有通配符、没有端口区间、没有裸 `*`；
  重复的 `host:port` 被拒。`tls` 必填，因为宿主既不升级也不降级连接。
- **每个插件同时最多四条连接。** 四条是并发上限，不是清单条数上限：端点白名单
  没有条数限制，有十台服务器的作者不必只挑四台。
- 插件拿到的是连接句柄与事件，永远拿不到套接字、流，也没有读取 TLS 会话的途径。
- TCP 连接上的 `credentialRef` 让宿主自己完成 IMAP 登录，且只走隐式 TLS：宿主
  读取 greeting、协商 PLAIN 或 LOGIN，仅交回 `authenticated: true`。登录后的
  字节流保持透明，服务器可能回显凭据。`tls: false` 端点被拒，也不提供
  STARTTLS、XOAUTH2 或 SMTP 相关能力。
- 插件卸载、被禁用或崩溃时，所有连接关闭。
- 用户的出网 HTTP 代理不适用于这些连接，安装审查会写明。

**入站 webhook（`inbound.webhook`）。**

- 监听、路径与令牌都由宿主持有。没有令牌的 webhook 根本不会注册；令牌是宿主生成
  的密钥，用常量时间比较，轮换是设置里的操作。
- 监听边界由 [ADR plugin-webhook-listener-boundary](/zh-CN/adr/plugin-webhook-listener-boundary)
  修订：局域网模式绑定所有接口并按来源地址过滤，不能保证排除所有公网来源。
- 传输是明文 HTTP，安装与设置里都会说明，措辞与非回环 HTTP MCP 端点一致
  （ADR 0142）：路径上的人可以读到内容，令牌是过滤，不是机密性。
- 正文超过 256 KiB 返回 `413`；每个 webhook 每分钟超过 120 次有效请求返回
  `429`。两个上限都能在 manifest 里调低，不能调高。
- 插件只收到宿主已经接受的请求，以事件形式；插件不能作答，宿主回 `202`。

**定时器（`scheduler`）。**

- 每个声明一个定时器，要么固定间隔、要么五段 cron，二者不能并存。下限一分钟；
  更快的声明直接校验失败，而不是被四舍五入。
- 触发粒度由宿主决定。定时器不是模型回合：一次触发调用插件处理函数，不消耗令牌。
- `runWhen: "idle"` 让宿主等用户空闲，`always` 是默认值。插件被禁用或卸载时不
  触发；错过的时间点合并为下一次机会的一次触发，而不是重放积压。
- 连续失败会停表并在插件页面显示，与受监管后台服务同一条规则。

**宿主写入列表（`mail.draft`、`notify.center`）。**

- `mail.draft` 把草稿写入宿主的草稿列表。**没有发送路径**，本决策不提供，也不藏在
  第二个权限后面。
- `notify.center` 往持久通知收件箱写一行，标明插件。家族有两个 kind：
  **`plugin.alert`** 是用户当下就该看到的一件事，**`plugin.digest`** 是插件汇总
  后代表一整批的一行；超过每小时限额的事件也由宿主折叠。`notify` 只显示横幅或
  系统通知，不落库；这也不是等待回答的 `prompt.*` 行。
- 两者与其它宿主队列一样有界：收件箱保留 200 条上限、由同一个用户操作清空，
  卸载插件会删除它的行。

**任务（`tasks.read`、`tasks.manage`）。**

- `tasks.read` 只读列出脱敏清单与账本事实，不含提示词、对话内容或凭据。
  `tasks.manage` 只创建并推进本插件的任务；其他任务返回 `NOT_FOUND`。
- 生效模式取请求值、manifest 上限、员工模式和 `accept-edits` 的最小值；
  省略请求值或上限时默认为 `accept-edits`。按动作审批落地前显式请求 `auto`
  会被拒绝。manifest 可声明 `auto`，安装或更新时说明当前上限，无单独确认框。
- 宿主对任务会话及其后代实施执行策略：内置低风险只读工具和 `accept-edits`
  下工作区内 Write/Edit 可自动放行，其余每次调用均需逐次批准。插件自报风险、
  子代理权限以及会话或持久授权不能放宽策略。工作区编辑包括覆盖及清空内容；
  命令或外部工具删除以及外部操作均需逐次批准。

### 4. 存储：架构 v43

能力相关的行存放在宿主自有的 SQLite 里：任务面与通知收件箱上的 `plugin_id`
标签，以及三张需要跨重启保存状态的能力表。`notifications` 需要重建，因为
`session_id` 必须变成可为空（插件条目没有会话），而 SQLite 改不了 `NOT NULL`
也放宽不了 `CHECK`。plugin 家族是 `plugin.alert` / `plugin.digest`，字段为
`plugin_id`、`title`、`body`、`link_json` 与 `dedupe_key`，
并用 `CHECK ((kind LIKE 'plugin.%') = (plugin_id IS NOT NULL))` 与收件箱其余
部分绑定——这是家族规则，而不是另一份要同步维护的 kind 清单。**重建时保持外键
约束开启**，因此会丢弃会话已经不存在的收件箱行；用户已授权丢弃它们，因为指向
已删除会话的条目没有任何东西可依附。

同一步还加上 `tasks.plugin_id` 与三张表：`plugin_webhook_events`（每条已接受
投递一行，记录对端地址与 `body_ref`——正文**不**存进 SQLite）、
`plugin_schedules`（上次尝试、连续失败次数与 `paused` 刹车，从不保存声明本身，
声明留在 manifest 里）与 `plugin_tcp_usage`（按插件、主机、端口与日期累计字节，
不是事件日志）。DDL 与幂等规则写在规格 `03-runtime/04-data-storage.md` 的
§4.14、§4.19d、§4.19e 与 §7。

**`tasks.origin` 保持 `('steward', 'direct')` 两个值。** 本决策的早期草案想给
CHECK 加 `'plugin'`，这一条**作废**。`origin` 记录的是哪条工作台路径派发了任务
——`steward` 是 1.7.0 之前的确认卡片，`direct` 是人自己用的界面——插件发起的
任务同样走这条 direct 路径。插件的参与是另一种来源信息，因此用可为空的
`plugin_id` 记录：不需要重建表、不改写任何历史行，也不会与既有两个取值混淆。

### 5. B-0 切片实现了什么

B-0 只做注册：

- `PLUGIN_PERMISSIONS` 里的八个名字，以及 `PLUGIN_PERMISSION_RISK` 中每个权限的
  风险等级；
- manifest 字段 `contributes.credentials` / `webhooks` / `schedules`、`net.tcp`
  与 `tasks`，含安装时的形状校验、各自的边界，以及「字段必须配权限」的规则；
- `packages/plugin-sdk` 中上述形状的类型与校验器。

最初的 B-0 切片不执行这些能力。后续 B1 实现凭据存储、状态查询以及宿主持有的
fetch 和 WebSocket 注入，并实现带凭据的 `net.tcp` 连接由宿主完成的 IMAP 登录；
B2 实现入站 webhook；B4 实现 `pi.notify.center`；B6 实现插件定时。`mail.draft`
与 `tasks.*` 按各自文档执行。

## 后果

- 插件可以申请这六项能力，用户能看见、限定并收回每一项。此前同样的行为是看不见的
  插件代码。
- 宿主多出六类它以前不持有的长生命周期资源：密钥、监听套接字、端点清单、定时器、
  收件箱行、任务。每一类都需要所有者和清理路径（卸载、禁用、崩溃、卸载安装、
  重启），这是实现工作量中更大的那一半。
- 权限仍然是契约与告知，不是围栏：带完整 Node 的插件主进程无论 `net.tcp` 怎么写
  都能自己开套接字（ADR 0008 D009）。改变的是：可审查的通道存在了，不可审查的
  通道不再是唯一选择。
- 风险表变成每个权限的必需一行。新增一项能力要在两张表里各加一行，漏掉第二处是
  编译错误。
- 收件箱在会话之外多了第二个所有者（插件）。`notifications` 的每个消费者——列表、
  未读计数、标记已读、清空、裁剪——都必须处理没有会话、没有回合的行。
- B4 已将 `Notification.session_id` 和 `session_title` 改为可选并读取插件字段，
  无会话的插件行不会使整个列表读取失败。
- `idx_notifications_plugin_dedupe` 在提供去重键时保证插件内部去重。

## 备选方案

- **让插件自持套接字、端口与令牌。** 否决：那正是现状，也正是用户无法审查的部分。
  禁用插件不会关掉宿主从不知道的端口。
- **提供密钥读取 API（`pi.credentials.get`）。** 否决：显式读取 API 会让意外
  记录或转发更容易。宿主代用不会主动返回保存的值，但不能隔离恶意插件代码。
- **用一个 `net.raw` 权限覆盖 TCP、UDP 与 TLS。** 否决：字面端点的 TCP 可审查；
  UDP 是另一种失败模式（无连接、源可伪造），需要自己的边界，因此不合并。
- **把 `net.tcp` 白名单限制为四条。** 否决：真正需要限制的是**同时四条连接**，
  它约束宿主的文件描述符与缓冲。限制条数只会限制作者，把有十台服务器的插件推回
  自己开套接字的老路。
- **只在非回环地址要求 webhook 令牌。** 否决：回环地址本机每个进程都能访问，而
  插件需要一条能依赖的规则。令牌在任何地址上都必需。
- **`tasks.origin = 'plugin'`。** 作废——见 §4。它改写了既有列的含义、逼出一次
  `sessions` 式的重建和历史行决策，并且与 `plugin_id` 已经说清的事情重复。
- **把 `auto` 作为 `maxPermission` 的默认值。** 否决：那等于让作者替用户决定
  批准步骤消失。
- **用 `notify` 承载收件箱行。** 否决：`notify` 是无存储、无所有者的瞬时横幅；
  `notify.center` 需要持久行、200 条上限、未读计数和卸载路径。把两者混为一谈，
  等于让每个弹过一次提示的插件都留下永久收件箱条目。
## 4. 多实例凭据槽位与 TCP 连接上限（2026-11-23，1.9.0）

本节修正上文的两处决定，其余决定不变。

### 问题

`contributes.credentials` 描述的是**一个**凭据：一个槽位、一份值。于是邮件插件只能
配一个账号，而它存在的意义——「盯住我的三个收件箱」——需要多个。剩下的出路只有三条：
每个邮箱一个槽位（清单无法知道用户有几个），把设置放在插件自己手里（脱离宿主的加密
存储、审计与卸载路径），或者让用户反复覆写同一份值来「假装」第二个账号。

另一个数字是同一件事的另一面：邮件插件要为每个账号常驻一条 IMAP 空闲连接，才能不靠
轮询收到新邮件。四条连接的上限下，五个邮箱插件光是待命就用掉了五条，剩下的工作没有
预算。

### 决定

1. 槽位可以声明 `multiple: { max }`（1..5）。不声明即保持已发布的单值槽位：存储键、
   `credentials.list` 的回答、`credentialRef` 写法都不变。向后兼容是硬要求，功能是
   增量叠加。
2. 实例存在加密的 secret store 里（`plugin:<id>:cred:<slot>#<instanceId>`），元数据
   放进插件既有的凭据索引。不改表结构；`<slotId>` 不含 `#`，所以引用语法没有歧义。
3. `credentialRef` 用 `"<slotId>#<instanceId>"` 指向一个实例。这类槽位只写槽位名返回
   `CREDENTIAL_INSTANCE_REQUIRED`；给单值槽位加 `#` 后缀是 `INVALID_ARGUMENT`。
   每条路径的闸门顺序不变：权限 → 出站白名单 → 槽位 → `scope ∩ net` → 读值。
4. 插件要能指名实例，就必须能认出实例。清单声明 `labelField`，它必须指向**非
   secret** 字段，`credentials.list` 返回每个实例的 id、显示名与非 secret 字段值。
   这是插件唯一能读到用户填写内容的地方，而且是刻意的例外：邮箱地址是插件区分账号的
   依据，不是秘密。每个 `secret` 字段在任何路径上都不可读。
5. 收集值仍是宿主的行为。`credentials.requestAdd` / `requestRemove` 请宿主弹出**自己
   的**表单，值经渲染层 → Main → host-core，从不经过插件进程。拒绝限制了打扰：
   窗口不在前台不弹框、同一插件同时只有一个对话框、达到 `max` 返回
   `CREDENTIAL_LIMIT`，以及用户关闭对话框后 30 秒冷却（模态框遮住整个应用，
   立刻重试等于把窗口从用户手里抢走）。用户已作答的对话框不进入冷却。插件靠 `credentials:changed` 知道要重读列表。
6. 既有的单值槽位升级为多实例槽位不会丢值：宿主先把已存 blob 复制成第一个实例，成功
   之后才删除原值；迁移出的实例 id 由槽位推导，中途失败后重试补完同一次迁移，而不是
   多出第二个实例。降级时把第一个实例写回并删除其余。两个方向都只按 id 记录审计，
   不记录值。
7. `MAX_CONNECTIONS_PER_PLUGIN` 从 4 提高到 8。这个上限约束的是宿主的描述符与内存，
   从来不是白名单条数。每条连接的待写缓冲、连接超时与 TLS 规则不动。

### 后果

- 插件从「一个邮箱」到「五个邮箱」不需要重写清单，已经配好一个账号的安装也无需迁移。
- `credentials.list` 的回答多了一种插件可以分支的形态：单值槽位仍回答
  `{id, configured}`，已发布的插件看不到不同的载荷。
- 对话框是插件触达用户的新路径。它被前台存在、单对话框所有权、超时与实例上限约束，
  并且每次都记审计。
- 每个插件八条连接仍是防止失控插件耗尽描述符的上限，不是按主机的预算。

### 备选方案

- **安装时按账号声明多个槽位。** 否决：清单无法知道用户有几个账号，等于在创作阶段
  就把功能封顶。
- **让插件用自己的表单收集值。** 否决：那会把明文放进宿主正要保护的那个进程，并放弃
  审计与前台规则。
- **只返回 `instanceId`、不返回显示名。** 否决：插件无法说明某一行是哪个账号，只能
  请用户记住一个不透明 id。
- **把 TCP 上限改成「无限制」。** 否决：有界才能防止一个插件的循环把宿主的描述符一起
  拖垮。八条足够「每个账号一条空闲连接」的设计，并留出连接本来要做的工作。

## 5. 用户自填的邮件服务器（2026-11-24，1.10.0）

本节修订第 3 节里的端点规则，并给第 4 节增加一项声明。本 ADR 其余内容继续有效。

### 问题

`net.tcp.connect` 只能连 `manifest.net.tcp` 里字面写出的端点，IMAP 凭据也只注入
槽位 `scope.domains` 里的主机——注入路径上有意不查 `net.anyHost`。于是邮箱插件无法
访问自建或公司的邮件服务器，因为任何清单都无法预先写出用户还没选的主机。现存的绕法
都更糟：按服务器拆槽位等于在创作阶段封死选择；`net.anyHost` 只放宽出网，仍带不走密码；
让插件自己收集服务器，则把「密码往哪发」的决定交给了插件。

### 决定

1. `contributes.credentials[].userEndpoint: { protocols: ("imap" | "pop3")[] }`，只有
   `imap` 槽位可以声明，非空且不重复。它为宿主预留四个**非密钥**字段键——
   `server`、`port`、`protocol`、`security`；同一槽位再声明这四个键之一会在安装时被拒，
   插件自己的表单因此永远写不进它们。
2. 服务器属于凭据实例：用户在宿主自有表单里、紧挨地址和密码填写，宿主只用同一实例里
   存下的服务器去登录该实例的密码。这个绑定替代了清单白名单与槽位 scope，也正是要点
   所在——插件没有任何位置可以把密码指向别处。
3. 用 `credentialRef` 指向这类实例的 `net.tcp.connect` 可以省略 `endpoint`，由宿主连
   用户存下的服务器；插件若给了端点，必须与存下的主机和端口完全一致，否则
   `PERMISSION_DENIED`。**没有** `credentialRef` 的连接永远到不了用户填写的服务器，
   因为那条路径仍要求 `manifest.net.tcp`。
4. 值的校验在宿主、在保存时，而不只在渲染层：裸主机名或 IP 字面量（不含协议、端口、
   路径、空白、通配符），端口 1..65535，协议须是该槽位声明的，加密方式只能是 `tls` 或
   `starttls`。私网与局域网地址依然有效——公司邮件服务器正是这个功能存在的理由；云
   元数据地址按出网策略同一份清单拒掉。`server` 留空表示「不使用自定义服务器」，实例
   走回预设路径，表单预填的另外三个键会被丢弃而不保存。
5. 传输安全是隐式 TLS 或 STARTTLS，宿主强制升级而不提供退路：服务器没有声明
   `STARTTLS`（IMAP）或 `CAPA` 里没有 `STLS`（POP3）就用一个独立的错误码拒绝；明文阶段
   读到的能力全部丢弃并在 TLS 上重新读取，所以未受保护的交换无法决定密码怎么发；升级
   达成之后再到的任何字节都会中止连接，这正是本契约要挡的 STARTTLS 注入。证书校验
   永不可选，SNI 用服务器名（IP 字面量改按地址校验）。
6. POP3 是宿主自己执行的第二种登录：`CAPA` 声明 `SASL PLAIN` 时用 `AUTH PLAIN`，否则
   `USER`/`PASS`，`-ERR` 即 `CREDENTIAL_REJECTED`。服务器接受之后，连接就像 IMAP 一样
   归插件。仍然没有 SMTP、没有明文登录、没有 OAuth2。
7. **没有** `userEndpoint` 的槽位与 1.9.0 逐字节一致：同样的存储形态、同样的白名单与
   scope 检查、同样的 connect 返回。没有新增权限——`net.tcp` 与 `credentials.use` 仍是
   全部开关——每插件连接上限也仍然作用于用户自填的连接。

### 后果

- 邮箱插件可以服务自建或公司服务器，宿主在创作阶段不需要知道任何主机名，也不需要新
  权限。
- 凭据变成一个两段式事实——秘密，以及它可以被发往哪里——绑定才有意义。换密码和换服务
  器一起保存，两者不会各自漂移。
- `credentials.list` 把这四个端点值作为 `publicFields` 报出，插件可以按服务器区分账号
  而读不到密码。
- 只有主动声明的槽位会多出这一段表单，其它槽位的渲染完全不变。
- 用户自填服务器的连接用一组封闭的失败码报告失败（`CONNECT_FAILED`、
  `TLS_CERTIFICATE`、`TLS_FAILED`、`STARTTLS_UNAVAILABLE`、`CREDENTIAL_REJECTED`），
  提示因此能说清要修什么，而不是笼统的「连接失败」。升级阶段也不会多出第六个名字。

### 备选方案

- **在清单里声明服务器。** 否决：清单不可能知道；而放宽成 `net.anyHost` 的槽位会把
  密码带到插件指定的任意主机。
- **让插件用自己的表单收集服务器并传进来。** 这正是本设计要禁止的重定向：等于由插件
  决定已存密码发往哪里。
- **允许明文，因为用户自己要的。** 否决：密码走在未加密的链路上不是一种偏好；
  不自带隐式 TLS 的服务器用 STARTTLS 覆盖。
- **接受自签名证书。** 否决：那会让「宿主校验了对端」在唯一有密码经过的路径上失去
  意义。

## 6. 取消账号数量上限（2026-11-24，1.10.0）

本节修订第 4 节第 1 点与第 5 点。其余内容继续有效。

### 问题

`multiple: { max }` 当初限定在 1..5，是因为预期邮箱插件为每个账号保持一条空闲连接，
而连接上限是四条。现在插件改成用短连接轮询，连接上限不再决定账号数——但宿主仍拒绝第
六个账号，这成了由实现细节发明的产品限制。用户需要的是「我有几个邮箱就几个」。

### 决定

1. `multiple` 可以省略 `max`。省略表示插件不设自己的上限；写出 `max` 时含义与已发布
   版本完全一致，允许范围放宽到 1..100。
2. 宿主保留一个内部上限：**每个槽位 100 个实例**。它保护加密存储与每插件的凭据索引
   不被单个槽位无限增长，也是返回 `CREDENTIAL_LIMIT` 的计数。它单独以 `limit` 报出，
   于是 `max` 仍表示「清单要求的那个数」，没声明上限的槽位不显示「x/y」。
3. `MAX_CONNECTIONS_PER_PLUGIN` 保持 8。放宽账号数不等于放宽并发：按账号开连接的插件
   仍会撞上它，这是插件要用短连接、错峰调度去解决的问题，而不是宿主该允许的事。
4. 既有 `max: 1..5` 的清单行为完全不变：同样的存储形态、同样的拒绝、同样的 `list`
   回答。声明了非法 `max` 的清单在安装时就被拒，而不是等到第一次读取。

### 后果

- 用户想加多少邮箱就加多少；插件无法用声明封顶，宿主也不会被做成无界列表。
- `credentials.status` / `credentials.list` 在可选的 `max` 旁多一个可选的 `limit`；
  已发布插件读到的 `max` 仍是自己声明的那个数。
- 设置页对没有声明上限的槽位只显示账号数，到宿主上限时仍会禁用「添加」。

### 备选方案

- **保持 5。** 否决：宿主已经不需要这个数，而且逼着有六个邮箱的用户来提 bug。
- **彻底不设上限。** 否决：无界列表就是无界的加密索引和无界的设置页。100 远超真实
  用户，同时仍然有界。
- **把 `MAX_CONNECTIONS_PER_PLUGIN` 一起提高。** 否决：那条上限约束的是描述符与缓冲，
  插件应当自己调度连接，而不是指望一个账号一条套接字。

## 2026-11-25 —— 每个邮箱账号自己的代理

背景：只能用隧道到达的邮箱（本机 Clash 后面的 Gmail IMAP、公司局域网网关后面的服务器）
此前根本无法使用。宿主自己拨原始 TCP 且不查代理——系统代理设置描述的是 HTTP 请求，而
原始套接字不是——所以唯一的办法是给整台机器开 TUN 模式。

### 决定

1. `contributes.credentials[]` 中 `kind: "imap"` 可声明**顶层**键
   `userProxy: { types: ("http" | "socks5")[] }`。顶层是刻意的：1.10.0 会忽略不认识的
   顶层槽位键，因此同一个包在 1.10.0 上仍能安装运行（只是没有代理）；而放在
   `userEndpoint` 里的未知键会被拒绝。
2. 代理属于凭据实例，和用户自填的服务器一样：宿主只在带该实例 `credentialRef` 的连接上
   走它，没有凭据引用的连接永远到不了。`userProxy` 与 `userEndpoint` 互不依赖，因为需要
   隧道的那类账号（Gmail）恰恰是沿用预设服务器的那类。
3. 宿主拥有五个保留字段键——`proxyType`、`proxyHost`、`proxyPort`、`proxyUsername`、
   `proxyPassword`——并拒绝把其中任何一个声明成字段的清单。前三个通过 `publicFields`
   发布（账号卡片因此可以说「经 127.0.0.1:7897」），两个凭据键从不发布，渲染层也无法
   预填它们。
4. 值由宿主在保存时校验，而不是表单：全有或全无（不选类型即不使用代理，其余键丢弃）、
   允许环回与私网／局域网地址（这正是功能本身）、云元数据地址按自定义服务器同一份清单
   拒绝、不含 CR/LF/NUL、每个代理凭据不超过 255 字节（RFC 1929）。
5. HTTP 用 `CONNECT host:port` 建隧道，可带 `Proxy-Authorization: Basic`；SOCKS5 先声明
   无认证，账号有代理登录时走 RFC 1929 子协商，然后 `CONNECT`；除非账号存的是 IP 字面量，
   地址按域名交给代理。本地不做任何解析：主机名正是代理存在的理由。代理应答之后多出来的
   字节属于下一阶段——STARTTLS 时那就是问候语。
6. TLS 不动：隐式 TLS 用邮件服务器的名字校验证书（绝不用代理的名字），STARTTLS 在隧道上
   的明文套接字里协商。没有直连退路，所以代理失败时连接就失败，而不是悄悄换一条路。
7. 五个失败码之外再加两个封闭名字：`PROXY_FAILED`（连不上、握手失败、拒绝建隧道）与
   `PROXY_AUTH_FAILED`（407、SOCKS 认证被拒）。都是固定文案，既不引用代理应答也不带凭据。

### 后果

- 用户可以让某一个邮箱走本机或局域网的代理，而不影响应用其它部分，插件也不会知道密码
  去了哪里。
- 插件的提示表多两个名字，代理账号因此能说清「代理没响应」还是「代理用户名或密码不对」。
- 代理登录是明文到达代理这一跳的。这是两种协议共同的性质，spec 里写明、表单提示里也说，
  也正是该功能面向用户自己或局域网代理、而非远端代理的原因。

### 备选方案

- **把代理放进 `userEndpoint`。** 否决：1.10.0 会拒绝那里的未知键，同一个包在插件仍要
  支持的宿主上直接装不上。
- **使用系统代理设置。** 否决：它们描述的是 HTTP 请求而不是原始套接字，而且是整机决定，
  面对的是账号级问题。
- **代理失败时退回直连。** 否决：那会一边报告邮箱可用，一边让密码从用户没有选择的路径
  离开。
- **本地解析邮件主机，再按地址连代理。** 否决：本地 DNS 正是这个位置上的代理要绕开的东西。

## 2026-11-25 —— 真正被读到的 catalog 宿主下限

背景：插件市场从未执行宿主下限。catalog 条目写 `minMinihAgent: ">=1.10.0"`，比较只认
裸版本号，读不懂的约束一律回答「可以装」——1.9.0 就是这样装上了为 1.10.0 构建的插件。

### 决定

1. 按范围前缀读取下限：`">=X.Y.Z"` 与裸 `X.Y.Z` 都表示「至少 X.Y.Z」，允许周围有空格。
2. 所有既有调用点本来就问同一个判断——安装／下载路径、更新检查、列表里的 `installable`
   标记——因此没有任何调用点需要改，它们只是开始得到正确答案。
3. 其它形式的范围维持本机一贯的宽松答案，并记一条 warn 日志：直接拒绝会把插件从所有读
   不懂该写法的宿主上藏起来，那比要修的这个问题更糟。
4. 清单侧的 `engines.minihAgent` 在本机并不作为门槛（只做归一化与保存，清单 schema 有
   说明），因此那里无需改动。

### 后果

- 钉在更新版本应用上的版本，不再在旧宿主上被提供、安装或作为更新推送。
- 安装对话框改说「先升级应用」，而不是抛一个 `PLUGIN_HOST_TOO_OLD` 原始失败：宿主报出
  所需版本时，提示里会点名该版本。
- 发布方写了本机读不懂的范围时仍能覆盖旧宿主，而告警让这种情况可见，不再悄无声息。

### 备选方案

- **拒绝一切下限读不懂的 catalog 条目。** 暂时否决：那会把插件从完全能用的宿主上藏起来，
  而且宽松答案在此次修复之前就存在。
- **支持完整的范围语法。** 作为范围否决：catalog 契约就是「至少 X.Y.Z」，实现完整的 semver
  范围比这个字段被承诺承载的东西大得多。

## 2026-11-25 —— 插件可以请用户指定一个保存位置

背景：邮箱插件拿到的附件是字节，而它没地方放。`pi.fs.writeText` 只能按插件的
`manifest.fs` 规则写文本、写不进沙箱之外，也没有任何二进制写入接口；而允许插件直接指定
绝对路径，等于把用户的整个文件系统交给它。

### 决定

1. `pi.fs.saveAs({ suggestedName, data, mimeType? })` 弹出原生「另存为」对话框，只写用户
   选定的那一个路径。权限是 `fs.write`，不套用 `manifest.fs` scope——用户在对话框里的选择
   本身就是授权，与其它「选文件」动作同一条规则。
2. 建议文件名只是**建议**：宿主把它压成单个路径段（去掉分隔符、控制字符与前导点，最长
   180 字节，什么都不剩时用 `attachment`），再交给对话框。
3. 边界：每次一个文件、最多 50 MiB、不能为空。应用自己的数据目录与一小串系统位置
   （`/System`、`/bin`、`/sbin`、`/usr/bin`、`/etc`、`/dev`、`/proc`、`/sys`）以
   `SAVE_AS_FAILED` 拒绝，取巧的文件名因此到不了宿主自己的状态。
4. 取消返回 `null` 且不写任何东西。目标路径不会回显到其它界面，审计只记录字节数与是否
   写了文件——绝不记录路径。

### 后果

- 插件能保存用户让它保存的东西，别的一概不行：一个对话框、一个文件、一个路径。
- 不新增权限：`fs.write` 本来就表示「这个插件可以往磁盘放文件」，对话框把它收窄成用户
  亲手选中的那一个。
- 写入发生在 Electron 主进程、紧挨着对话框，取消时磁盘上什么都不会发生，也没有哪条宿主
  RPC 需要把字节传两遍。

### 备选方案

- **新增带 scope 的 `fs.writeAbsolute` RPC。** 否决：那会让插件在用户没看的情况下写到
  scope 里的任何位置，正是对话框要消除的危险。
- **复用 `fs.writeText` 并传 base64。** 否决：它仍在沙箱根之内（用户选的文件夹根本到不了），
  而且 base64 会把 25 MiB 的附件膨胀成宿主还得解码的字符串。
- **不问用户，直接存进固定的「下载」目录。** 否决：用户要的是存到自己指定的位置，静默的
  位置比一个对话框更糟。

2026-11-25 修订（审查）：`saveAs` 只实现一份，插件进程（`pi.fs.saveAs`）与面板通道共用——
附件字节是在插件进程里拿到的，只做面板通道是错的。每个插件同时只能有一个对话框
（`SAVE_AS_BUSY`），因为插件可以在没有用户操作时调用。`refusedSavePath` 改用 `relative`
比较，Windows 的分隔符与大小写因此成立，并在 Windows 上额外拒绝 `%SystemRoot%`、
`C:\Windows`、`C:\Program Files( x86)` 与 `C:\ProgramData`。

## 2026-11-25 —— 由宿主代发邮件（`mail.send`）

背景：邮箱插件能读邮箱，却回不了信。读信是宿主代做的——插件点名一个
`credentialRef`，宿主自己连接、登录，再把流交回去——但同一个插件没有任何发信
通道，「写回去」只能停在草稿。现有的退路都比问题更糟：插件可以用 `net.tcp`
自己开 socket 再向用户要一次密码（把秘密放进了凭据模型本来要挡住的那个进程），
或者借用 `mail.draft`，而那份授权的全部含义正是「从不发送」。

### 决定

1. 新增第十个权限 **`mail.send`**，风险 **high**：宿主握着账号、会话和投递，
   而发出去的信收不回来。`mail.draft` 含义不变，其条目改为「草稿从不发送，发送是
   另一份授权」。
2. API 为 `pi.mail.send({ credential, endpoint?, envelope, mime, timeoutMs })`
   → `{ accepted, rejected, messageId? }`。插件只点名账号（声明的 `imap` 槽，
   多实例槽再加实例 id）和报文，永远拿不到密码、socket、连接句柄或服务器原文。
3. 发信端点与收信端点同源决定：
   - **预设**：`endpoint` 必须是 `manifest.net.tcp` 的字面条目且落在槽
     `scope.domains` 内，校验函数与 IMAP 预设路径共用。声明的 `tls: true` 走隐式
     TLS；`tls: false` 走**必须成功的 STARTTLS**，绝不明文认证、也不留明文会话。
   - **账号自己的服务器**：`contributes.credentials[].userSend: { security:
     ("tls" | "starttls")[] }`（仅 `imap` 槽）为宿主保留三个非密字段键
     `sendServer`、`sendPort`、`sendSecurity`，由宿主自己的凭据表单填写，与该账号的
     密码存在同一个实例里。实例的密码只会被送到同一个实例里存的端点；这样的账号
     插件再传 `endpoint` 一律 `INVALID_ARGUMENT`——比读信路径更严，因为插件没有
     任何理由再点一次账号已经配置好的服务器。
   - **两者都没有** → `MAIL_SEND_NOT_CONFIGURED`。
   预设路径同样对**存了自填收信服务器**（`userEndpoint`）的账号关闭：读信已经锁在
   那个端点，发信必须一起锁住。否则同一个密码会被插件指派的任意一个声明 SMTP 收走
   ——那是与用户填写的服务商完全不同的一家，正是自填服务器模型要挡住的改投，也超出
   下面接受的「同槽 scope 内另一家声明端点」这一风险范围。这类账号只有在也存下自己的
   发信服务器之后才能发信；在那之前答案是 `MAIL_SEND_NOT_CONFIGURED`，不发出任何连接。
   `userSend` 是**顶层**槽键，理由与 `userProxy` 相同：1.10.0 宿主会忽略不认识的
   顶层键，同一个包在那边照样装得上，只是继续走预设路径。`sendServer` 留空表示
   「不自己发信」，另两个键随之丢弃。发信用户名与密码沿用收信那份——能读邮箱的账号
   就是发信的账号。
4. 连接是**宿主内部连接**：`PluginTcpRegistry.acquireInternal` 与插件可见的连接共用
   并发配额、超时、TLS 规则和按账号的代理，但不发任何 `net:tcp:*` 事件、不交出
   `connectionId`，插件既列不出也关不掉；它随插件释放、禁用、重载、崩溃一起结束，
   其 `signal` 能中断会话。配了代理的账号照旧走代理，不回退直连。
5. 会话完全属于宿主：问候 → `EHLO` → `STARTTLS`（升级后重新读 capabilities；约定
   之后到达的字节直接中断）→ `AUTH PLAIN`/`LOGIN` → `MAIL FROM` → 逐个 `RCPT TO`
   → `DATA`（CRLF 规范化、行首点转义）→ `QUIT`，并受总超时与 abort 信号约束。
   服务器没有 `8BITMIME` 时拒绝 8 位内容，否则服务器会改写报文。
6. 防滥用（都在会话前或会话中强制）：信封发件人、报文 `From:` 与任何 `Sender:`
   必须是账号自己的地址；不接受 `Bcc:` 头（密送写在信封里）；每封最多 50 个去重
   收件人、25 MiB；单个插件滚动一小时内最多 30 封。计数在内存里，重启清零——它挡的
   是一个失控的循环把账号变成中转站，不是拿账号向主人限量。审计只记插件、实例、
   收件人数、字节数、结果和错误码，不记正文、主题和任何地址。
7. 失败以封闭的码集回到插件：`MAIL_SEND_NOT_CONFIGURED`、`AUTH_FAILED`、
   `RECIPIENT_REJECTED`（附被拒地址）、`SENDER_REJECTED`、`MESSAGE_REJECTED`、
   `MAIL_FROM_MISMATCH`、`MAIL_BCC_HEADER`、`MAIL_TOO_LARGE`、
   `MAIL_RATE_LIMITED`、`MAIL_EIGHT_BIT_UNSUPPORTED`、`SMTP_FAILED`，加上 TCP
   一半已有的 `CONNECT_FAILED`、`TIMEOUT`、`TLS_FAILED`、`TLS_CERTIFICATE`、
   `STARTTLS_UNAVAILABLE`、`PROXY_FAILED`、`PROXY_AUTH_FAILED` 与凭据类拒绝。
   任何文案都不引用服务器原文。
8. 纯增量：没有 `userSend` 的槽与 1.10.0 完全一致；没有声明 `mail.send` 的插件
   触碰不到这些能力。

### 影响

- 邮箱插件可以回信，而全程不持有密码；用户也能在账号表单里看到自己的信从哪台
  服务器发出。
- 宿主多了一种需要拥有和拆除的长连接；它复用 TCP registry 的配额与释放路径，而不是
  再加一套拨号逻辑。
- 插件消息表多出十来个名字，每个都说清该修什么，而不是「发送失败」。
- 同一个 `net.tcp` 条目现在按调用方有两种含义：`net.tcp.connect` 是透明流，
  `mail.send` 是只能走 STARTTLS 的提交会话。这一点写在 manifest spec 与本 ADR 里，
  也是 `tls: false` 的邮件端点绝不会明文使用的原因。
- 预设账号仍可能把某个实例的凭据投往同槽 scope 里另一家的声明端点：绑定粒度是槽，
  与既有 IMAP 预设登录一致。这个残余风险在这里写明，而不是悄悄继承。

### 备选

- **让插件用 `net.tcp` 自己跑 SMTP。** 否决：带 `credentialRef` 的 `net.tcp` 由
  宿主登录后把透明流交给插件，而 SMTP 登录需要在会话开始前就拿到密码——这条路要么
  把秘密交给插件，要么逼用户自己把密码告诉插件，正是凭据模型要避免的两种结果。
- **给 `manifest.net.tcp` 条目加 `starttls: true`。** 否决：对这个调用方，`tls:
  false` 已经表达「可连接、且凭证之前必须先升级」，第四个字段会让同一个端点在作者
  记住哪个标志时出现三种含义；无论如何升级都是强制的。
- **复用 `mail.draft`。** 否决：草稿之所以是 medium 风险，正是因为它发不出去；放宽
  它等于把所有已安装它的插件静默升权。
- **单独要一个 SMTP 密码。** 否决：对几乎所有账号它就是同一个服务商、同一个密码，
  第二个字段只是多一种把账号存成半配置状态的方式。
- **允许自填发信服务器账号接受插件点名的端点（读信路径的「必须完全一致」规则）。**
  否决，属于多余面：发信是从插件已握着的报文组合出来的，不存在需要回指服务器的
  断线重连场景。
- **按固定小时桶计数。** 否决：09:00 发 30 封、09:30 再发 30 封就能过一个桶，而
  服务商看到的是半小时 60 封。窗口是滚动的。
- **持久化计数器。** 暂时否决：为一个「保护账号不被失控插件拖走」的上限加一次 schema
  版本不值得；ADR 选择明确写出重启清零，而不是藏着它。
