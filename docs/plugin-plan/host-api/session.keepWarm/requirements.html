会话缓存保活 · 需求

用户已经定下的部分与 agent 建议的部分分开写。拍板过的规则不改，实现里觉得可行的做法归在建议里。

status: implemented

01用户已定

  • 静默。保活请求不往对话里插任何行，也不是一次对话轮次。不走 agent/prompt，不走 continueTurn。
  • 可见性靠会话级状态。插件在输入区右侧显示开关、下次时间、今日花费；被跳过或停止时显示原因。
  • 默认值。间隔 50 分钟（可调 30–55）；连续 4 次保活期间没有真实轮次就自动停；每个会话每天估算花费上限 1 美元；某次保活缓存读取占比低于 50% 判定缓存已失效并停下；上下文小于 2 万 token 不保活；模型范围默认只开 Claude，GPT 可选；每个会话的开关默认关闭。
  • 宿主判定。能不能发由宿主决定，不满足就返回原因：会话忙、还没有过真实请求、模型/服务商/思考强度换过、前缀变了、距上次真实请求超过约 57 分钟、协议不支持。
  • 请求与真实请求一致。同一条组装路径、同样的 headers 与亲和、同样的 tools 与思考参数，只在末尾追加一句固定的极短 user 消息。不为省钱调低思考强度或换模型。
  • 完全隔离。不执行工具、不写对话或 transcript、不触发 turn hook / session:turnEnded / 通知 / 标题生成 / 静默重跑 / progress 续跑，不改会话最近活跃时间与未读状态。
  • 让路。真实轮次开始就取消正在进行的保活，保活永远不阻塞、不排在用户消息前面。
  • 用量落库。新增单独的账本，不伪造 turn 行，带迁移，兼容老数据，能计入现有用量统计并能区分出来。

02接口

项值
方法pi.session.keepWarm({ sessionId })
权限session.keepWarm 安装时确认；没有它调用直接被拒（PERMISSION_DENIED），不会走到宿主。
参数sessionId：非空字符串，≤128 字符。
返回warmed 带 usage 与 cacheReadRatio；skipped 带 reason；failed 带 reason。三种都带 model: { providerId, modelId }，让插件能按自己的模型范围停下而不用另开读会话的权限。
副作用一次宿主发起的模型请求，一次落库。对话、transcript、事件流都不变。

03跳过原因

reason含义插件是否该继续排期
session_busy有正在跑/排队/等审批的轮次，或在压缩中是，稍后重试
already_running这个会话已有一个保活请求在飞是，稍后重试
no_prior_request进程启动后没见过这个会话的真实请求否，等下一次真实轮次
model_changed服务商 / 模型 / 思考强度 / 协议换过否
prefix_changed重新组装出来的前缀与上次真实请求的指纹不同否
prefix_expired距上次真实请求超过 57 分钟否
context_too_small上下文不足 2 万 token否
protocol_unsupported这个协议没法在非轮次里拿到用量否
runtime_unavailable会话不存在、会话已删、运行时起不来否

04场景

  • 正常保活。会话空闲 50 分钟，前缀没变 → 一次 warmed，用量与缓存占比回到插件，今日花费增加。
  • 提示词变了。系统提示里的日期或记忆笔记更新过 → prefix_changed，一分钱不花，插件停下并显示原因。
  • 用户回来了。保活请求在飞时用户发消息 → 保活被 abort，用户消息不受影响。
  • 缓存本来就在衰退。某次保活缓存读取占比 31% → 插件按 50% 阈值停下，不再花钱。
  • 没有该权限。插件没拿到 session.keepWarm → 调用被拒，宿主从未收到请求。

05不做什么

  • 不替插件排期、不重试、不做退避。失败就是失败，理由交回去。
  • 不为了保活改模型、改思考强度、改输出上限：输出上限沿用上一次真实请求的值，因为更小的 max_tokens 会在把 Responses reasoning 翻译成 Anthropic thinking 的网关上改掉思考预算，反而破坏缓存。
  • 不保活一个已经超过缓存寿命的会话。
  • 不把保活当成轮次，也不为了让用量有地方放而造一个轮次。

06agent 建议（实现里采用的做法）

  • 前缀指纹记在 sidecar 进程里而不是运行时实例上：运行时 30 分钟就被回收，首次保活在 50 分钟。重启后指纹丢失、按“还没有过真实请求”跳过，这在拍板时是可接受的。
  • 宿主的两次判定分工：主进程判会话在不在、能不能起运行时；sidecar 判前缀、协议、上下文与时限。两边都返回同一套 reason。
  • 用量表 keep_warm_usage 只追加，跳过也落一行（花费 0），这样“为什么昨晚没保活”能查。
  • 模型身份随每次回答返回。插件拿不到别人会话的模型（session.read.own 只看自己导入的会话），因此“只保活 Claude”在第一次回答后生效：代价是那个会话被保活一次，之后停下。
